# ADR 编号台账 ADR-LEDGER

**这个文件存在的理由**：ADR 编号原来是每条分支各自「预支」的——两条分支在同一 base 之后各自新增 ADR，编号就有很高概率撞（[ADR-029] 与 [ADR-068] 两次实例）。台账最初把「取号」串行化为「开工前先登记」，但这个假设在**批量并行**拉 worktree 时不成立：几条分支同时 fork，谁也没等到别人的登记先合并、就已经各自读到了同一个「下一个空号」——2026-09-04/05 的 PR69-72 一批因此连撞四次（070→071→072→073→074→075，各自独立算出同一个号，直到合并那一刻才暴露）。

**现改为：分配延后到「合并进 main」这一刻**（[ADR-076]）。无论并行开多少条分支，合并进 main 永远是串行的（[ADR-069] 已规定一次只合一个后台 PR），把取号绑在这个天然串行的动作上，而不是绑在「分支开工」这个天然并行的动作上，就不会再撞。

**纪律（[ADR-076] 起生效）**：

- 分支开工时**不写具体数字号**。`DECISIONS.md` 新增条目的标题写占位符：`### ADR-PENDING-<分支名或简短主题> — <一句话主题>`；正文和其他文件里对它的交叉引用也写 `[ADR-PENDING-<同一占位符>]`，不要猜数字，不用再开「只改本文件的快速 PR」预登记。
- **合并协调者串行合并某条后台 PR 之前**，在该分支上跑一次 `make assign-adr`（即 `python tools/assign_adr_number.py`）：读取 main 当前台账最大号，把这条分支引入的占位符依次分配真实编号、全库替换所有引用、往台账追加登记行；改动只 stage，人工确认 diff 后照常提交，再走 `gh pr merge`（步骤序列见 `PROJECT/GIT-RUNBOOK.md`）。交互式会话直接在自己分支上跑这一步即可。
- **多个待合并 PR 都带占位符时仍要逐条处理**：定号 → 合并 → `make build` 绿了，再处理下一个的定号——不要一次性给所有待合并分支批量定号，那样又变回「预支」竞态。
- 真撞了（两条分支的定号脚本恰好在同一瞬间基于同一个 main 状态各自跑，概率已经从「批次内几乎必撞」降到这种极窄窗口）：仍按 [ADR-029] 协议晚合并方让号 + 全库 grep 改所有引用兜底。
- `make check` 校验（`validate.py`）：**main 上**残留 `ADR-PENDING-*` 占位符是硬错误（合并前忘了跑定号脚本）；**其他分支上**允许残留、只给警告（未定号是分支未合并前的正常中间态，不阻塞该分支自己的 `make build`）。台账本身仍要求 `DECISIONS.md` 每条已定号的 `### ADR-NNN` 都登记过、编号 `1..max` 连续不重复（判定逻辑不变，仍是 [ADR-069] 定的 `adr_ledger_violations`）。

事实（每条 ADR「定了什么 / 为什么」）的唯一权威仍是 `DECISIONS.md`；本文件只登记「号被谁占了」，主题一句话即可。
